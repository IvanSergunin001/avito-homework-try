# План реализации: Авито.Кухня (MVP)

Документ фиксирует решения, принятые до написания кода, и порядок работ. Он же — тот самый
«промпт (plan), по которому написан проект», который ТЗ просит приложить. Текст задания — `TASK.md`.

## 1. Границы MVP

Делаем:

- каталог: список заведений, карточка заведения, меню заведения, товар по id, поиск по названию;
- оформление заказа с синхронной проверкой у заведения;
- статус заказа и отмена;
- продвижение статусов заведением;
- сервис-заведение как самостоятельная «коробка» для заведений без собственных систем.

Не делаем: аутентификацию и авторизацию (прямо запрещено ТЗ), корзину на сервере (живёт на клиенте),
платежи, доставку, рейтинги, админ-UI.

## 2. Стек

Go 1.27, chi, PostgreSQL, `log/slog`, конфиг через `github.com/knadh/koanf` (только ENV + `.env.example`,
`.env` в `.gitignore`), миграции — goose CLI v3.28.0, спецификации — OpenAPI + `oapi-codegen`,
тесты — `testcontainers-go`, линтер — `golangci-lint` с собственным `.golangci.yml`.
Запуск — `docker compose up`. Локально Go не установлен: сборка, линт, генерация и диаграммы идут в контейнерах.

## 3. Архитектура

Два bounded context'а, общающихся только через опубликованный контракт:

- **Platform** — Авито.Кухня;
- **RestaurantBox** — коробка заведения.

Тактический DDD без domain events, CQRS и outbox: агрегат `Order` (корень, позиции внутри, инварианты и
матрица переходов — методами агрегата), агрегат `Restaurant` с меню, value-object'ы `Money`, `Quantity`.
Слои: `domain` (не импортирует инфраструктуру) → `application` (use cases) → `adapters`.

```
cmd/platform, cmd/restaurant
internal/platform/{domain, application, adapters/{http, postgres, restaurant_client}, migrations}
internal/restaurant/{domain, application, adapters/{http, postgres, platform_client}, migrations}
internal/pkg/{config, problem, logger, testdb}
api/{platform.v1.yaml, partner.v1.yaml, admin.v1.yaml}
docs/{adr, puml, img}
compose.yaml  Makefile  .golangci.yml  .env.example  .gitignore  README.md  TASK.md
```

Каталоги и имена пакетов — snake_case (`restaurant_client`); проверки имён пакетов в `stylecheck`/`revive`
отключены точечно, с комментарием в `.golangci.yml`.

## 4. Поверхности API

Всё под `/api`, `/healthz` — в корне (пробы не версионируются).

- Клиент `/api/v1`: `GET /restaurants`, `GET /restaurants/{id}`, `GET /restaurants/{id}/products`,
  `GET /products`, `GET /products/{id}`, `POST /orders`, `GET /orders/{id}`, `POST /orders/{id}/cancel`.
- Партнёр `/api/partner/v1` (заголовок `X-Partner-Key`): `POST /catalog/refresh`,
  `POST /orders/{id}/status` (callback статуса).
- Админ `/api/admin/v1` (заголовок `X-Admin-Token`): `POST /restaurants`, `PUT /restaurants/{id}`,
  `POST /orders/{id}/cancel` (отмена «через саппорт»).

Пользователь — `X-User-Id: <uuid>` в заголовке. Отдельной таблицы `customers` нет: она не даёт гарантий,
раз источник идентификатора внешний. Вводить её стоит, когда появятся скидки по тратам за период,
история и профиль.

Пагинация — `limit`/`offset` (по умолчанию 20, максимум 100), поиск — `ILIKE` с индексом `pg_trgm`.
Курсорная пагинация и полнотекстовый поиск — в roadmap.

Карточка заведения и его меню — разные ручки: меню это коллекция неограниченного размера со своей
пагинацией и кешированием. Цена — лишний round-trip на открытии экрана.

## 5. Контракт «площадка ↔ заведение»

Отдельный OpenAPI-документ (`partner.v1.yaml`) — это продукт для сторонних заведений, а не побочный артефакт.
Заведение обязано реализовать: страничную выдачу меню, приём заказа, отмену заказа; площадка предоставляет
заведению ручку callback'а статуса и ручку внеочередного обновления каталога.

Коробка сверх контракта умеет: CRUD меню и стоп-лист, просмотр входящих заказов и ручное продвижение статусов
(рабочее место оператора), собственное хранилище. Флаг `AUTO_ADVANCE_ORDERS` двигает статусы по таймеру —
для демонстрации CJM без ручных вызовов; в проде выключен.

## 6. Каталог: pull-модель

Площадка сама тянет меню фоновым воркером (интервал из ENV, по умолчанию 30 с): upsert по
`(restaurant_id, external_id)`, исчезнувшие позиции деактивируются. Заведение может попросить обновиться
немедленно — `POST /api/partner/v1/catalog/refresh` с `X-Partner-Key`.

Защита воркера: таймаут запроса, `io.LimitReader` на 20 МБ, потоковый декод, потолок на число позиций.
При превышении лимита синк **отменяется целиком**, старый каталог остаётся нетронутым — частично применённое
меню хуже устаревшего. Само меню в контракте страничное (500 позиций на страницу), поэтому упереться в 20 МБ
может только заведение, нарушающее контракт. Входящие тела запросов площадки ограничены `MaxBytesReader` в 1 МБ.

## 7. Оформление заказа

`order_id` (uuid v7) генерирует клиент и передаёт в теле — он же ключ идемпотентности:

- повтор (`unique_violation`) → 200 и тот же заказ;
- тот же id с другим составом (расхождение `request_hash`) → 422 `idempotency_key_reuse`;
- id принадлежит другому `customer_id` → 409 без деталей;
- uuid **v7** (монотонный), чтобы клиентский PK не разносил вставки по индексу.

Заказ пишется в БД со статусом `pending` до вызова заведения. Далее синхронный вызов в заведение с
`Idempotency-Key` и `X-Attempt-Number` (номер попытки — чтобы заведение могло распознать возможный дубль).
Заведение — источник истины по наличию и цене; отказы: `out_of_stock`, `price_changed`, `unknown_product`,
`restaurant_closed`. На `price_changed` площадка инициирует внеочередной pull меню и отдаёт клиенту 409 с новой ценой.

Двухфазный резерв (`POST /reservations` + `confirm` с TTL) осознанно не делаем: он честнее решает гонку за
последней позицией, но добавляет два состояния в контракт и фоновую уборку протухших резервов. Описан в README
как следующий шаг с условием, при котором окупается.

## 8. Статусы заказа

Нетерминальные: `pending` → `under_review` → `confirmed` → `cooking` → `delivering`.
Терминальные: `completed`, `cancelled` — переходов из них нет, любой callback на терминальный заказ возвращает
200 и ничего не меняет (защита от ретраев). Переходы монотонны: «старый» статус после нового отбрасывается.

Кто двигает: `pending` — площадка при создании; `under_review` — успешный синхронный ответ заведения;
дальше — только callback'и заведения.

Отмена:

- клиент — из `pending`, `under_review`, `confirmed`; из `cooking` и позже — 409 `order_not_cancellable`
  (продукты уже потрачены);
- заведение после начала готовки — **не через партнёрский API, а через саппорт**:
  `POST /api/admin/v1/orders/{id}/cancel` с обязательным `reason`, `cancelled_by = support`.
  Причина — списание продуктов, компенсация клиенту и защита от злоупотреблений; на CJM заведения это
  отдельная ветка «звонок в саппорт».

Вся матрица — в `Order.TransitionTo(status, actor)`; хендлеры правил не знают.

## 9. Схемы БД

Две схемы в одном инстансе PostgreSQL, **без единого внешнего ключа между ними** — это физическая граница
контекстов. Деньги — целые копейки (`price`, `total` типа `int64`): `float` для денег не годится
(`0.1 + 0.2 != 0.3`), а `numeric` в Go всё равно вырождается в строку или float.

`platform`:

- `restaurants(id, name, base_url, api_key_hash, is_active, last_synced_at)`
- `products(id, restaurant_id, external_id, name, description, price, is_available, is_active, updated_at,
  UNIQUE(restaurant_id, external_id))`
- `orders(id uuid, customer_id uuid, restaurant_id, status, total, address, items jsonb, request_hash,
  cancelled_by, cancellation_reason, created_at, updated_at)`
- `order_status_events(id, order_id, status, actor, occurred_at)` — аудит и дедупликация callback'ов

`restaurant`:

- `products(id, name, description, price, stock, is_available)`
- `orders(id, platform_order_id, idempotency_key, status, address, total, items jsonb)`
- `status_callbacks(id, order_id, status, attempts, next_attempt_at, delivered_at)` — очередь ретраев

Позиции заказа — `jsonb` внутри `orders`: заказ это агрегат, позиции не имеют самостоятельной жизни и всегда
читаются целиком, цена и название хранятся снимком (заказ не должен меняться задним числом при обновлении
каталога), инварианты проверяет домен. Теряем удобные `GROUP BY` для аналитики — но в компании масштаба Авито
аналитика всё равно живёт в отдельной системе, а не в OLTP. В маленькой компании правильнее была бы
нормализованная таблица: выгрузки делались бы прямо из этой базы. Обратный путь — backfill одним
`SELECT` + `INSERT`.

## 10. Ошибки

`application/problem+json` (RFC 7807) с extension-полем `code` для машиночитаемой причины
(`out_of_stock`, `price_changed`, `unknown_product`, `restaurant_closed`, `order_not_cancellable`,
`idempotency_key_reuse`). Коды: 400 — валидация, 404 — нет сущности, 409 — доменный конфликт,
422 — переиспользование ключа идемпотентности, 502/504 — заведение недоступно.

## 11. Тесты, линтер, конфиг

- unit на домен без моков (переходы статусов, подсчёт суммы, правила отмены);
- интеграционный тест на **каждую** ручку; внешнее заведение в тестах площадки — `httptest`-заглушка;
- сквозной e2e «каталог → заказ → статусы → отмена» через compose с реальной коробкой;
- `internal/pkg/testdb`: по умолчанию поднимает Postgres через testcontainers; `TEST_DB_DSN` — использовать
  внешнюю БД из compose; `TEST_KEEP_DB=1` — не убивать контейнер после прогона и напечатать строку подключения
  (чтобы заглянуть в базу после тестов). Брейкпоинты работают в любом режиме — это обычный `go test`.

Миграции накатывает goose CLI отдельным сервисом compose (микро-образ с бинарём из релиза); сервисные бинари
не содержат goose и не мигрируют на старте. `make migrate-up`, `make migrate-status`, `make migration name=...`.

## 14. Упрощения и почему они приемлемы

| Упрощение | Почему приемлемо на MVP | Что в проде |
|---|---|---|
| Нет аутентификации, пользователь — `X-User-Id` | ТЗ прямо запрещает делать авторизацию | OAuth/JWT, `customer_id` из токена |
| Партнёрский ключ в заголовке, админ-токен из ENV | это не аутентификация пользователя, а минимальная защита интеграционных ручек | mTLS или подписанные запросы, ротация ключей |
| Один инстанс PostgreSQL на два контекста, разные схемы | границы соблюдены логически (нет FK между схемами) | отдельные БД у площадки и партнёра |
| Синхронный вызов заведения без outbox и очереди | видно поведение целиком, нечего дебажить в фоне | outbox → очередь с DLQ, реконсиляция, circuit breaker |
| Позиции заказа в `jsonb` | заказ читается целиком, аналитика — во внешней системе | либо так же, либо нормализация под нужды отчётности |
| `limit`/`offset` + `ILIKE` | каталог демо-масштаба | курсорная пагинация, полнотекст/поисковый движок |
| Корзина на клиенте | не влияет на серверные инварианты | серверная корзина ради кросс-девайса и аналитики брошенных корзин |
| Нет метрик, только логи | инфраструктуру мониторинга в MVP не поднимаем | метрики из раздела 16 + алерты |
| Демо-данные seed-миграцией, адрес заведения — админ-ручкой | нет онбординг-флоу партнёра | полноценный онбординг с модерацией |

## 15. ADR

1. Pull-каталог с триггером обновления вместо push от заведения.
2. Синхронное оформление заказа вместо двухфазного резерва.
3. Позиции заказа как часть агрегата (`jsonb`), аналитика — вне OLTP.
4. `order_id` от клиента как ключ идемпотентности вместо таблицы `idempotency_keys`.
5. Идентификаторы пользователя и партнёра в заголовках вместо аутентификации.
6. Два bounded context'а и коробка заведения как самостоятельный продукт.

## 16. Corner cases и надёжность

- **Заведение часто отменяет заказы и просит вернуть их в работу.** Если это станет заметным паттерном —
  дать заведению окно 2–5 минут (или «до момента, когда пользователь оформил новый заказ»), в течение которого
  отменённый заказ возвращается в работу, либо ввести задержку перед уведомлением клиента об отмене.
  Так пользователь не увидит отмену, которую заведение через минуту откатило.
- **Площадка упала после ответа заведения** — заказ висит в `pending`; лечится повтором по тому же `order_id`.
- **Ретраи callback'ов** — экспоненциальный backoff, 3 попытки, приём идемпотентен за счёт монотонности переходов.
- Roadmap надёжности: transactional outbox вместо прямого вызова, очередь с DLQ, реконсиляция «сирот»,
  circuit breaker на недоступное заведение.

## 17. Метрики и алерты (в README, реализация — за рамками MVP)

- `catalog_sync_failed_total` — алерт на серию неудач по одному заведению;
- `catalog_sync_limit_exceeded_total` — отдельный алерт, это всегда сломанный партнёр;
- `order_place_restaurant_errors_total`;
- `status_callback_retries_exhausted_total`.
